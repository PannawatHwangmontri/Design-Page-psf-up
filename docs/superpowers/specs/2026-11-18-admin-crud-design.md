# ขอบเขต CRUD ของหน้าแอดมิน (สมมติว่ามี backend, แอดมินคนเดียว)

สถานะ: ร่างสำหรับพิจารณา ยังไม่ได้อนุมัติ และยังไม่ได้เลือกวิธีสร้าง
วันที่: 2026-11-18
ที่มา: ผู้ใช้ขอให้จำลองตัวเองเป็นผู้ดูแลเว็บ แล้วคิดว่าหน้าแอดมินควรแก้ เพิ่ม ลบอะไรได้บ้าง

## 1. เป้าหมาย

ให้ผู้ดูแลเว็บ "มาตรฐานอาจารย์มืออาชีพ" (UP PSF) คนเดียว จัดการข้อมูลทุกอย่างที่ปรากฏบนเว็บและทุกขั้นตอนของใบสมัครได้เอง โดยไม่ต้องแก้ไฟล์โค้ด

หลักคิดที่ใช้ตัดสินว่าข้อมูลใดควรอยู่ในแอดมิน:

1. ถ้าข้อมูลเปลี่ยนตามเวลาหรือตามปี (ข่าว ปฏิทิน ผู้ผ่านเกณฑ์ ประกาศ) ผู้ดูแลต้องแก้เองได้
2. ถ้าข้อมูลเป็นของผู้ใช้ (บัญชี ใบสมัคร หลักฐาน) ผู้ดูแลต้องดูและจัดการได้ แต่ไม่ควรเขียนทับสิ่งที่ผู้ใช้กรอก
3. ถ้าข้อมูลเป็นหลักฐานของการตัดสิน (สถานะ ผลประเมิน) ต้องเก็บเป็นประวัติ ห้ามแก้ย้อนหลัง

## 2. ข้อสมมติ

- มี backend และฐานข้อมูลจริง แทน localStorage ที่ใช้ในเว็บตัวอย่างตอนนี้ (`src/lib/site.tsx`, `src/lib/applicant.ts`)
- แอดมินมีคนเดียว จึงไม่มีบทบาท สิทธิ์ย่อย หรือบัญชีแอดมินหลายคน
- เว็บรองรับ 2 ภาษา (TH/EN) ข้อความทุกชิ้นที่แสดงบนเว็บต้องมีทั้งสองภาษา
- ปีใช้ พ.ศ. ในข้อมูล และแปลงเป็น ค.ศ. ตอนแสดงภาษาอังกฤษ (เหมือนที่ `admin-schema.ts` ทำ)

## 3. ปัจจุบันทำอะไรได้แล้ว

อ้างอิงจาก `src/app/[lang]/admin/page.tsx`, `src/data/admin-schema.ts` และ `src/app/[lang]/admin/applications/page.tsx`

| ส่วน | สถานะปัจจุบัน |
|---|---|
| ข่าว/กิจกรรม | เพิ่ม ดู แก้ ลบ ได้ (วันที่ หัวข้อ ข้อความย่อ ภาพ ไฟล์ PDF) |
| ประกาศ | เพิ่ม ดู แก้ ลบ ได้ (ปี ชื่อ ไฟล์ PDF) |
| ผู้ผ่านเกณฑ์หน้าแรก | เพิ่ม ดู แก้ ลบ ได้ (ชื่อ คณะ ระดับ ปีที่ผ่าน รูป) |
| ผู้ผ่านเกณฑ์ตามปี | เพิ่ม ดู แก้ ลบ ได้ ภายในกลุ่มปี |
| ปฏิทินการประเมิน | เพิ่ม ดู แก้ ลบ กิจกรรมได้ (รอบ ประเภท วันเริ่ม วันสิ้นสุด) |
| เอกสารปฏิทิน | เพิ่ม ดู แก้ ลบ ได้ (ปี ชื่อ PDF) |
| แบบฟอร์ม | เพิ่ม ดู แก้ ลบ ได้ (ชื่อ PDF วันที่อัปเดต) |
| ข้อความทั่วไป | แก้ได้บางกลุ่ม (ทั่วไป เมนู หน้าแรก รายละเอียด ประเมิน ประชาสัมพันธ์ ดีเด่น เอกสาร ความเป็นมา) |
| ใบสมัคร | ดู และตั้งสถานะ หมายเหตุ ติ๊กรับรองจากต้นสังกัด |
| ล้างข้อมูล | มีปุ่มคืนค่าเริ่มต้นปุ่มเดียว |

ช่องว่างที่พบ:

- รายการคู่มือ/ประกาศ PSF จริง 8 ไฟล์ (`manuals` ใน `src/data/mock.ts`) และโปสเตอร์ปฏิทินหน้าแรก (`calendarPoster`) ผู้ดูแลแก้เองไม่ได้
- FAQ (`pages.faq`), หน้าติดต่อ (`pages.contact`), เกณฑ์ผู้สมัคร (`pages.eligibility`) ไม่อยู่ใน `contentGroups` ของ `admin-schema.ts` จึงไม่ปรากฏในแท็บข้อความทั่วไป (ตรวจจากรายชื่อกลุ่ม ยังไม่ได้ไล่ตรวจทีละฟิลด์)
- หน้าตรวจใบสมัครไม่มีค้นหา กรอง ส่งออก ดูไฟล์หลักฐาน หรือลบ/เก็บถาวร
- ข้อมูลอยู่ใน localStorage ของเบราว์เซอร์ที่แก้ ผู้เข้าชมคนอื่นไม่เห็นสิ่งที่แอดมินแก้ ไฟล์แนบเก็บเป็น dataUrl จึงชนเพดานพื้นที่ราว 5MB
- ล็อกอินแอดมินเป็นรหัสตัวอย่างฝังในโค้ด

### 4.2 ใบสมัครและหลักฐาน

โครงใบสมัครปัจจุบันอยู่ที่ `src/lib/applicant.ts`: ชื่อ คณะ ตำแหน่ง ระดับที่ขอ คำอธิบาย 3 องค์ประกอบ (ความรู้ ทักษะการสอน คุณค่าของครู) วันเริ่มปฏิบัติงาน ประวัติการปฏิบัติงาน ผลงาน สถานะ ไฟล์หลักฐาน 5 ชนิด (แบบฟอร์ม ประเมินตนเอง ประวัติ แผนการสอน ผู้บังคับบัญชา) ประวัติสถานะ และข้อความ

| ข้อมูล | C | R | U | D | พฤติกรรมที่เสนอ |
|---|---|---|---|---|---|
| ใบสมัคร | ✗ | ✓ | ✓ | ✗ | ผู้สมัครเป็นคนสร้าง แอดมินดู ค้นหา กรอง แก้ได้เฉพาะฟิลด์ของแอดมิน (สถานะ หมายเหตุ รับรอง) ไม่ลบ ใช้ "เก็บถาวร" แทน |
| สถานะ/ผลตัดสิน | ✓ | ✓ | ✗ | ✗ | แต่ละการเปลี่ยนสถานะเป็นแถวใหม่ในประวัติ พร้อมเวลา ห้ามแก้ย้อนหลัง |
| หมายเหตุ/ข้อความถึงผู้สมัคร | ✓ | ✓ | ✗ | ✗ | ผู้สมัครเห็นข้อความที่แอดมินเขียน ต้องมีเวลากำกับ |
| การรับรองจากต้นสังกัด | ✓ | ✓ | ✓ | ✗ | แอดมินติ๊กเอง เพราะไม่มีบัญชีผู้แทนคณะ ควรบันทึกวันที่และผู้ยืนยัน |
| ไฟล์หลักฐาน 5 ชนิด | ✗ | ✓ | ✗ | ✗ | ผู้สมัครอัปโหลด แอดมินเปิดดูและดาวน์โหลดในหน้าเดียวกับใบสมัคร |

กฎของสถานะที่ระบบต้องรักษา (ตรงกับของเดิม):

- สถานะมี 5 ค่า: ยังไม่ยื่น, รอพิจารณา, ผ่านระดับ 1, ให้แก้ไขแล้วยื่นใหม่, ไม่ผ่าน
- "ให้แก้ไขแล้วยื่นใหม่" ใช้ได้ครั้งเดียวต่อใบสมัคร (`MAX_RESUBMITS = 1`) ครั้งถัดไปต้องเป็นผลสุดท้าย
- ใบสมัครที่ยื่นแล้วล็อกการแก้ไขจนกว่าผู้สมัครถอนกลับ และถอนได้เฉพาะตอนรอพิจารณา

เครื่องมือในหน้ารายการใบสมัครที่ควรมี: ค้นหาชื่อ, กรองตามรอบ/ปี/สถานะ/คณะ/ระดับ, เรียงตามวันที่ยื่น, ส่งออก CSV, ตัวนับจำนวนต่อสถานะ

## 5. เรื่องที่ต้องตัดสินใจเพิ่มเติม

### 5.1 ที่ตัดออกเพราะแอดมินคนเดียว

- ตารางบทบาท/สิทธิ์ และบัญชีแอดมินหลายคน
- ผู้แทนคณะกดรับรองเอง (แอดมินติ๊กแทน)
- กรรมการประเมินและคะแนน (ตัดไว้ก่อน ถ้าจะให้ระบบเก็บผลประเมินในอนาคตต้องเปิดเป็นงานใหม่)
- บันทึกประวัติการแก้เนื้อหา (audit log) ใช้ถังขยะและสำรองข้อมูลแทน แต่ประวัติสถานะใบสมัครยังต้องเก็บ

### 5.2 ผู้ผ่านเกณฑ์: กรอกเองหรือสร้างจากใบสมัคร

ตอนนี้ผู้ผ่านเกณฑ์เป็นข้อมูลแยกที่แอดมินกรอกเอง ถ้ามี backend ควรมีปุ่ม "ประกาศผล" ที่คัดลอกชื่อ คณะ ระดับจากใบสมัครที่ผ่านไปสร้างรายการผู้ผ่านเกณฑ์ ข้อดีคือไม่กรอกซ้ำ ข้อควรระวังคือผู้สมัครต้องยินยอมให้เผยแพร่ชื่อและรูป

### 5.3 ข้อควรระวังด้านความปลอดภัยของแอดมินคนเดียว

เพราะมีบัญชีเดียวที่ทำได้ทุกอย่าง บัญชีนี้จึงเป็นจุดเสี่ยงเดียว ควรมี:

- รหัสผ่านที่เก็บแบบแฮช ไม่ใช่รหัสตัวอย่างฝังในโค้ด
- จำกัดจำนวนครั้งที่ล็อกอินผิด
- ช่องทางกู้คืนรหัสผ่านที่ไม่ต้องพึ่งคนอื่น
- ยืนยันก่อนทำการที่กู้คืนไม่ได้ (ลบถาวร ล้างข้อมูล)
- ไฟล์ที่อัปโหลดจำกัดชนิด (PDF/รูป) และขนาด ตรวจฝั่งเซิร์ฟเวอร์

### 5.4 ข้อมูลส่วนบุคคล

ใบสมัครและหลักฐานมีข้อมูลบุคคลจริงเมื่อใช้งานจริง เว็บตัวอย่างใช้ข้อมูลสมมติเท่านั้น ถ้าใช้จริงต้องมีนโยบายเก็บและลบข้อมูล และผู้สมัครต้องเห็นเฉพาะของตัวเอง

## 6. คำถามที่ยังเปิดอยู่

1. ผู้สมัครลบบัญชีตัวเองได้ไหม หรือให้แอดมินลบอย่างเดียว
2. ต้องการส่งอีเมลแจ้งสถานะใบสมัครหรือไม่ (มีผลต่อแม่แบบข้อความและบริการส่งอีเมล)
3. ผู้ผ่านเกณฑ์ที่ประกาศบนเว็บ ต้องขอความยินยอมจากเจ้าตัวในระบบหรือไม่
4. หน้า `/outstanding` ต้องการรายชื่อรายปีจริงหรือไม่ หรือคงเป็นข้อความอธิบายโครงการ
5. จะเก็บข้อมูลที่ไหน (บริการฐานข้อมูลของมหาวิทยาลัยหรือบริการภายนอก) มีผลต่อการเลือกเทคโนโลยี backend

## 7. ลำดับความสำคัญที่เสนอ

1. ย้ายคู่มือ/ประกาศ PSF, FAQ, โปสเตอร์ปฏิทิน, หน้าติดต่อ, เกณฑ์ผู้สมัคร เข้ามาแก้ในแอดมิน (เพิ่มใน `admin-schema.ts` ไม่ต้องมี backend)
2. หน้ารายการใบสมัคร: ค้นหา กรอง ดูหลักฐาน ส่งออก CSV เก็บถาวร
3. ตั้งค่ารอบ ที่คุมการเปิด/ปิดรับสมัคร
4. สำรอง/นำเข้า JSON และถังขยะ
5. ต่อ backend จริง: ล็อกอิน ฐานข้อมูล คลังไฟล์ แล้วย้ายทุกอย่างจาก localStorage

ข้อ 1 ถึง 4 ทำและสาธิตในเว็บตัวอย่างได้ก่อนมี backend ข้อ 5 เป็นงานแยกที่ต้องวางแผนต่างหาก

## 8. วิธีสร้าง (ยังไม่เลือก)

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| ก. ขยายแอดมินเดิมใน localStorage ก่อน (ข้อ 1-4) | เร็ว เห็นผลทันที ไม่ต้องมี backend | ข้อมูลไม่ถึงผู้เข้าชมคนอื่น ต้องย้ายภายหลัง |
| ข. ทำ backend ก่อน แล้วย้ายแอดมินไปทั้งหมด | ได้ระบบใช้งานจริงครั้งเดียว | งานใหญ่ ต้องตัดสินเรื่องที่เก็บข้อมูล ความปลอดภัย การปฏิบัติตามกฎหมายข้อมูลส่วนบุคคล |
| ค. ทำ ก. ก่อน โดยแยกชั้นเก็บข้อมูลให้สลับเป็น backend ได้ทีหลัง | ได้ของสาธิตเร็วและย้ายง่าย | ต้องออกแบบชั้นเก็บข้อมูลเพิ่มเล็กน้อย |

คำแนะนำ: ทางเลือก ค. เพราะเว็บนี้เป็นเว็บตัวอย่างที่ต้องโชว์ให้เห็นภาพ แต่ผู้ใช้เป็นผู้เลือก
